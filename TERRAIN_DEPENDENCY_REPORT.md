## 2. Shackleton anomaly investigation, evidence, root cause, and resolution

**Conclusion: no implementation defect found. The 14–27° horizon at every azimuth is genuinely supported by the DEM. The mask and sidecar were left unmodified.**

Evidence gathered, in order:

1. **Fitted near-field plane is a real outlier.** Shackleton's R3 7×7/70m plane fit gives `slope_deg = 20.06°` (vs. IM-2's `2.78°` and CY-3's `0.52°` at the same window size). This alone would explain a much higher near-zone contribution than the other two sites.
2. **Direct DEM inspection confirms the fit, not a fit bug.** A 150m×150m raw elevation window around the exact site pixel (`row=500,col=500`, distance from the true site coordinate = 5.76 m, i.e. correctly centred) shows a consistent ~75m elevation change diagonally across ~200m — an independently-measured ~21° slope, matching the plane fit almost exactly. 100% of the window is valid DEM (no nodata).
3. **Raw (unfiltered, no-near-zone) DEM-only raycast of the near crop alone** shows real terrain horizon ranging from **−5.75° to +26.0°** depending on azimuth — i.e. genuinely dramatic local relief, not a flat artifact.
4. **The 14–27° published floor comes from the mid crop (6–14 km), not the near-zone occluder.** Cross-referencing the published mask's per-azimuth distance field against the raw near-crop-only raycast shows every bin in the lowest-horizon sector (az 300–330°, where the near crop alone shows only −5.75° to −4.66°) is actually sourced from DEM terrain at 13.4–13.9 km, not from the near-zone formula (which would report `distance = d_min_m/1000 = 0.03 km`). Direct inspection of that 13.8 km point shows a real, 100%-valid, +1738 m peak — a height difference of ~4057 m over 13.8 km (~16.3°), consistent with the observed value. **No nodata/edge artifact exists in that annulus (0 of 1,343,063 pixels invalid).**
5. **Coordinate pixel placement, azimuth convention, and CRS are all consistent** with the already-production-verified code path used successfully for IM-2 and CY-3 (same `masks.py`/`horizon.py`, same frame convention, same CRS for all 3 crops as confirmed in the sidecar).

**Interpretation:** the catalogued coordinate (`lat=-89.54, lon=129.0`, sourced from USGS/NASA CLPS material per `sites.yaml`) sits in terrain that is locally steep (~20° over a 70 m baseline) and is genuinely surrounded by tall, nearby crater-rim terrain in most directions within ~14 km. This is consistent with the well-known fact that the Shackleton–de Gerlache "ridge" high-illumination point is an extremely narrow (meter-scale) saddle; a catalogued reference coordinate even tens of meters off that exact saddle can land on a slope with much higher local horizons than the saddle itself. **No evidence was found that the coordinate is wrong**, and per the task's explicit instruction, it was **not** altered. This is a catalog-ownership question (Gowri owns `sites.yaml`) best resolved by checking whether a more spatially precise saddle coordinate exists in the cited authoritative sources — not something to silently infer or move here.

No files were changed for this investigation; the published mask/sigma hashes are unchanged.

## 5. 0 m observer-height decision

**No action taken — the premise does not match the current code.**

- `web/src/state/scenarioStore.ts`: `export type MastHeightM = 1 | 2 | 5 | 10;` — there is no `0` option.
- Every height-selector UI (`DefinitionsEditor.tsx`, `TouchdownPad.tsx`) and `urlSync.ts` hardcode `[1, 2, 5, 10]`. No `0` appears anywhere in the committed frontend.
- If a 0 m option is later proposed: numerically the raycaster and near-zone formula are both well-defined at `h=0` (no division by zero, no singularity), so the backend *could* compute it without a code change. However, adding it would require a **new, incompatible Tier-A contract version** — `height_count` is baked into the 64-byte binary header (`4`), the elevation/distance array lengths (`57600` bytes each) and total file length (`115264`) all assume exactly 4 heights; adding a 5th height changes every one of these and requires regenerating every existing Tier-A mask/sigma artifact for every site, per `data_masks.md` §10's explicit "any change to dimensions... requires a new incompatible contract version and coordinated producer/consumer approval." This is a cross-team decision, not something to do unilaterally here.
- Recommendation to Abhinav: there is nothing to remove today (no 0 m UI option exists). If one is planned, treat it as a breaking contract change requiring sign-off and full regeneration, not a quick addition; a ground-level (mast-less) observer is also a degenerate case relative to any real instrument height, worth re-confirming is actually wanted before investing in the contract bump.

## 6. PSR naming and coordinate-convention verification

**Coordinate convention: verified correct, numerically, against ground truth.** Using `pyproj.Transformer` against the actual producer CRS string (`+proj=stere +lat_0=-90 +lat_ts=-90 +lon_0=0 +R=1737400 +units=m +no_defs`), the frontend's `project()` formula (`x = r·sin(lon_east)`, `y = r·cos(lon_east)`, top-left image origin) matches pyproj's output **exactly** at 4 independent test points (lon = 0°, 90°, 180°, 270° at lat −80°). This is not a self-consistency round-trip check (which would also pass if signs were flipped symmetrically) — it's an independent ground-truth comparison. A new regression test (`web/src/engine/__tests__/projection.test.ts`) pins these exact values and passes.

**Naming: two legitimately different artifacts were found sharing confusingly similar names:**
1. `contracts/data_terrain_misc.md` §4.1's `psr_distance.bin/json` — a single, merged, `uint16`-quantized evaluator raster consumed by `web/src/engine/data/psr.ts`'s `loadPsr()` (used for the Basemap hover-distance readout). **This has never been implemented by any producer** — a genuine, standalone gap, unrelated to extent naming.
2. `pipeline/lumen_pipeline/terrain/psr.py`'s `generate_psr_distance_layer(extent)` — **already implemented**, writes `psr_distance_80_90S.{bin,json}` and `psr_distance_85_90S.{bin,json}` as per-extent `float32` ground-distance rasters. This is the §5.3 item 5 "Distance-to-PSR" Tier-1 map layer, correctly named to match every other S-7 layer's per-extent convention. It is schema-incompatible with (1) (`float32` vs `uint16`, per-extent vs merged, different field names).

I updated `contracts/data_terrain_misc.md` (§4.1 and §5.3 item 5) to explicitly disambiguate these two artifacts by name and schema, and to document the Tier-1 layer's deliberate PNG-format deviation (it's a continuous-valued binary raster, not a palette PNG like the other four layers). If Abhinav's loader change targets `psr_distance_80_90S.*`, it is correctly targeting the already-implemented Tier-1 map layer — not a broken/renamed version of the still-missing evaluator raster. The evaluator raster itself remains a real, separate, unimplemented gap.
